# 方案工作台审查问题修复（SP-001 ~ SP-004）

- 日期：2026-11-02 · 开发者：Claude Code · 模块：core（会话历史、行业包调整物料）、web（方案工作台）

## 任务卡
- **背景**：另一个 agent 在线上（销售张晨、星河设计工作室软件外包需求）审查方案工作台，记录了 4 个问题。用户要求再审一遍，然后修复。
- **做法**：对照代码逐条找原因，确认 4 条都成立后再改，每条都补了回归测试。

## 逐条核实与修复

| 编号 | 问题 | 核实出的原因 | 修复 |
|---|---|---|---|
| SP-001 | 需求卡删了「服务项目展示」、加了「会员积分」后确认，刷新后需求卡恢复成初始版本，与报价不一致 | 确认的需求只写进了本轮图状态 `confirmed_requirement`，没有存在消息上；历史记录只能还原 AI 最初推送的草稿卡 | `prepare_chat` 把确认时的需求快照存进这条用户消息的 `additional_kwargs.requirement`；`history._history` 还原时用它替换上一张需求卡，并标 `confirmed`。前端需求卡显示「已确认」，不再显示按草稿算的粗估区间 |
| SP-002 | 经济版把订单管理改成 8 人天，切到标准版再切回来，改动丢了，也没有提示 | `AiMessage` 只有一份 `edits`，换档位时 `setEdits({})` 直接清空 | 改为按档位分别保存（`editsByTier`），切走再切回来还在；确认时只带当前档位的调整 |
| SP-003 | 删掉或改了物料后，确认区「配置」仍显示原来的「6 个功能模块、约 57 人天」 | 前端 `adjustTier` 和后端 `adjust_tier` 都只重算金额，`summary` 原样沿用 | 新增 `adjustedSummary` / `adjusted_summary`（前后端同一口径）：调整后摘要写「人天合计 X 人天（原方案约 Y 人天）；去掉 …；改了 N 项数量」。人天只算单位是「人天」的物料，部署上线（次）不算。改过物料的档位卡片标「原方案参考」 |
| SP-004 | 打开较早生成的待确认报价，点取消，显示「已完成 0 步（用时 2460 秒）」 | 确认 / 取消后续写沿用这条回复原来的 `startedAt`，等待确认的时间被算进耗时；没有步骤时也显示了步骤栏 | `applyDecision` 把开始时间往后挪掉等待的那段（历史会话打开的从点击时算起）；没有步骤、已有正文时不显示步骤栏 |

## 校验与兜底
- **审查报告的「预期」没有全部照做**：SP-003 建议「按当前物料重新汇总模块数」。模块数要知道哪些物料是功能模块，这是软件外包行业包的内部约定（`MOD-` 开头的 SKU），放进通用的 `packs/base` 违反「行业相关只放 packs 目录」的规则。所以改为列出去掉的物料名和人天合计，工期也不估算（报告也说工期按业务规则算，不要求按人天线性增加）。
- **回归测试先在未修复的代码上跑过**：SP-001 的接口测试在旧版 `history.py` 上失败，换回修复版后通过。
- 用 Python 脚本改文件时，Windows 默认把换行写成 CRLF，git 提示后统一转回 LF。
- 本轮没有改接口结构：历史消息的 artifact `data` 本来就是任意 JSON，OpenAPI 不变。
