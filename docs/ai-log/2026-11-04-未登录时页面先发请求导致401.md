# 没登录或登录失效时，页面先发一批请求全部 401

- 日期：2026-11-04 · 开发者：Claude Code · 模块：web（SessionProvider、AppShell）
- 上一份：`2026-11-04-AI报价档位与毛利前后不一致.md`

## 任务卡
- **背景**：用户在线上看到，登录后浏览器里仍有 3 个接口返回 401：`/api/expenses?view=mine&page=1&page_size=50`、`/api/templates`、`/api/notifications?limit=20`。用户担心筛选、模板、通知失效或数据不同步。
- **做法**：先在本地复现「临时密码登录 → 强制改密码」，再查线上 core 日志（只读），对照请求的先后顺序。

## 查到的事实
- 本地走「临时密码登录 → 改密码」：所有请求都是 200，没有复现。
- 线上 core 日志里，每次 `POST /api/auth/login 200` 之前，都紧挨着这 3 个请求的 401。也就是说，401 发生在登录**之前**，不是登录之后。浏览器开着「保留日志」时，它们会留在列表里，看起来像登录后出现的。
- 原因：页面外壳（侧栏的通知、跟进模板）和页面本身（报销列表）一挂载就发请求；登录状态是之后才检查的。没有 token，或 token 已失效（这次线上重置演示账号密码后，旧登录全部作废）时，这批请求先各 401 一次，然后才跳到登录页。
- 登录后的请求本身没有问题，所以页面数据正常，筛选、模板、通知也不受影响。但每次打开页面都多出一批 401，日志里也很乱。

## 修改
- `lib/session.ts` 新增 `sessionVerified`：`/api/me` 成功才算核实。401 和没有 token 都不算；网络错误、服务不可用不拦着，交给页面显示错误。
- `SessionProvider` 提供 `ready`，核实过一次后就一直保持，免得切换角色时整个页面收起来。
- `AppShell` 在 `ready` 之前只显示底色，不渲染侧栏和页面，所以没核实之前不会发出任何业务请求。
- 回归测试：`lib/__tests__/session-verified.test.ts`。

## 验证（本地页面）
- 用的是本地临时测试账号，验证完已删除：
  - 没有 token 时打开 `/expenses`：除了登录页本身的 `/api/auth/options`，没有任何 API 请求，直接跳到登录页；
  - 正常登录：先 `/api/me 200`，再请求通知、模板、报销，全部 200，页面正常显示；
  - 登录后让 token 失效（`token_version + 1`，并等认证缓存的 15 秒过去）再打开 `/expenses`：core 只收到一个 `/api/me 401`，随后跳到登录页。
- web vitest 395 个通过；typecheck / lint 通过。
## 浏览器自动化测试（Playwright，Edge）
- 本地 `.env` 开着企业微信推送，测试前的检查会拦下来，不让测试运行。没有改 `.env`，而是用临时的 compose 覆盖文件把 core 的 `WECOM_WEBHOOK_URL` 置空后重启；跑完恢复原样，确认推送来源回到 env。
- 全量 117 个：93 个通过，24 个失败。逐个看了原因：
  - **本地环境（不改代码）**：
    - 本地开着个人模式，报销、报价自动通过，主管也能管配置。审批、报销提交、定时任务、通知跳转、审批批量、超标文案这几项，测试都按需要主管审批来写；
    - 演示数据被之前的测试和走查改过：团队默认产品线变成了软件定制开发，AI 出方案走了软件外包行业包，报价相关的 5 个用例拿不到确认卡；演示商机「合同审查私有化」已经赢单，没有「出方案」按钮；
    - 真实模型超时（core 日志里有 `Request timed out`）：日报 AI 草稿为空、AI 用量接口 500，以及几个等确认卡的 AI 用例。
  - **测试本身过时，已改**：
    - `settings.spec.ts`、`v7.spec.ts`：个人模式加了「工作方式」分组，排在第一个，用例改成先切到「报价与审批」；
    - `v4.spec.ts` 选住宿日期：固定选本月 10、12 号，每月上旬这两天还没到，选不了。改成选不了时先退到上个月。
  - **真实问题，已修**：合同页顶部三格在 320px 手机上，加载骨架固定 112px 宽，超出了格子。加了 `max-w-full`。登录核实后页面才渲染，测量正好落在加载阶段，问题才暴露出来。
- 重跑改过的用例：手机布局、登录（7 个）、业务规则、住宿日期选择都通过。住宿用例之后还有一条断言失败，是个人模式下的文案不同（「需主管审批」），属于环境原因。
- 没有在干净环境（`seed --reset` 且关掉个人模式）下重跑全量。
