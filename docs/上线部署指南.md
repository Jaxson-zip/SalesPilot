# 上线部署指南

本地开发用 `docker compose up -d`；正式上线在它上面叠加 `docker-compose.prod.yml`。两者的区别：

| | 本地开发 | 正式上线（叠加 prod） |
|---|---|---|
| 对外端口 | db 5432、core 8000、网关 8100、web 3000 都开放 | 只开放 nginx 的 80 / 443，其余只在容器内网互通 |
| 崩溃 / 服务器重启 | 不自动拉起 | 自动拉起（`restart: unless-stopped`） |
| 登录方式 | 演示账户一键进入 | 默认 `DEMO_LOGIN=false`，只能账号密码登录 |
| 配置检查 | 默认密钥只打警告 | 默认密钥、默认数据库密码直接拒绝启动 |
| 来源 IP | 只认连接对端 | 读 nginx 写入的 X-Real-IP（登录失败锁定按真实客户端计数） |
| 容器日志 | 不限大小 | 每个服务最多 5 × 20 MB 轮转 |

## 一、上线前检查清单

逐项打勾再对外开放：

- [ ] `.env` 里 `JWT_SECRET` 是 32 位以上随机串（`openssl rand -hex 32`）
- [ ] `GATEWAY_INTERNAL_KEY` 与 `LLM_GATEWAY_KEY` 相同，且是随机串
- [ ] `MODEL_KEYS_SECRET` 是 32 位以上随机串（网页上填写的模型 Key 用它加密）
- [ ] `POSTGRES_PASSWORD` 是随机强密码（**首次启动前**改；见下文「已有数据卷改密码」）
- [ ] `DEMO_LOGIN=false`（或不写，prod 默认就是 false）
- [ ] `ACCESS_CODE` 按需设置（内部系统建议设，多一道门）
- [ ] `WEB_BASE_URL` 改成对外地址，例如 `https://sales.example.com`（企业微信推送里的链接用它）
- [ ] `NGINX_PORT=80`
- [ ] 至少一家模型厂商的 Key：可以写在 `.env`，也可以上线后由管理员在「系统设置 → 模型接入」里填写并测试连接；知识库需要 Embedding 模型，服务器要能访问对应厂商
- [ ] 证书已放到 `infra/nginx/certs/`（第三节）
- [ ] 云服务器安全组只放行 80、443（以及你自己的 SSH 端口）
- [ ] 第一个管理员已建好、临时密码已改（第四节）
- [ ] 备份定时任务已配置，并**实际恢复过一次**（第五节）
- [ ] 行业包里的示例价格和知识库示例文档已换成真实资料（README「AI 学习问答」一节）

## 二、启动

```bash
git clone <仓库> /srv/salespilot && cd /srv/salespilot
cp .env.example .env && vi .env          # 按清单填写
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.prod.yml ps   # 全部 healthy / running
```

为了少打字，可以在服务器上设一个别名：

```bash
alias dc='docker compose -f docker-compose.yml -f docker-compose.prod.yml'
```

core 起不来时先看日志：`dc logs core | tail -50`。如果看到「正式模式（DEMO_LOGIN=false）拒绝启动：…」，按提示改 `.env` 后 `dc up -d core`。

## 三、HTTPS

1. 在云厂商申请免费证书（腾讯云 / 阿里云都有，下载「Nginx」格式），或用 certbot。
2. 把证书放到服务器：`infra/nginx/certs/fullchain.pem`、`infra/nginx/certs/privkey.pem`（这个目录已在 `.gitignore` 里，不会被提交）。
3. 不用改任何配置文件：`docker-compose.prod.yml` 已经把 `infra/nginx/https.conf` 挂成 nginx 的配置（HTTP 跳转到 HTTPS，`server_name _` 对任何域名都生效），证书到位后 `dc up -d nginx` 即可。
   - 不要在服务器上改入库的文件：自动部署会 `git reset --hard origin/main` 对齐仓库，本地改动会被覆盖。要改 nginx 就改仓库里的 `https.conf` 再推送。
   - 本地 `docker compose --profile prod` 用的是只有 HTTP 的 `default.conf`（本地没有证书）。
4. 验证：`curl -I http://你的域名` 返回 301 跳转到 https；浏览器打开地址栏有锁。
5. 证书到期前要续期（免费证书一般 3 个月到 1 年），换完文件 `dc exec nginx nginx -s reload`。

如果前面还有云负载均衡（CLB / SLB）做 HTTPS，nginx 只监听 80 即可，但要在 `infra/nginx/snippets/proxy.conf` 里改用 `real_ip` 模块取负载均衡传来的真实地址，否则所有人的来源 IP 都是负载均衡的地址。

## 四、账号初始化

### 空库上线（推荐）

不要导入演示数据（`python -m seed` 会带进假客户、假合同和公开密码的演示账号）。只建第一个管理员：

```bash
dc exec core python -m seed.admin admin --name 系统管理员
# 输出：已新建管理员：admin / 临时密码：xxxxxxxxxx
```

用它登录，首次登录会强制改密码；然后在「系统设置 → 成员与团队」里建团队、建销售和主管账号（同样是临时密码，首次登录强制改）。行业包对应的产品线由这个命令一并建好。

### 沿用演示库

如果要在演示数据基础上继续用，至少：

1. 先清掉测试数据（`docker compose exec core python -m seed --reset`，会重置成干净的演示数据，并清掉试用者录入的全部业务数据；要求输入 RESET 确认，非交互加 `--yes`），或者干脆空库重来；
2. 把四个演示账号的密码重置掉——正式模式下它们**不能再用公开的 `demo2026` 登录**，会提示用下面的命令：

   ```bash
   dc exec core python -m seed.admin zhoumin    # 已存在的账号：只重置密码，角色不变
   ```

   不用的演示账号在「成员与团队」里停用。

忘了管理员密码也用同一条命令找回。

## 五、备份与恢复

数据都在两个 Docker 数据卷里：`pgdata`（数据库，含知识库向量和 AI 会话）和 `uploads`（票据、样例图片、知识库原文件）。

### 备份

```bash
infra/backup/backup.sh                 # 默认写到 ./backups，保留 14 天
KEEP_DAYS=30 infra/backup/backup.sh /data/backups
```

每天凌晨自动备份（`crontab -e`）：

```cron
30 3 * * * cd /srv/salespilot && infra/backup/backup.sh >> backups/backup.log 2>&1
```

**备份只放在同一台机器上不算备份**：硬盘坏了、机器被删会一起丢。再加一条同步到对象存储（腾讯云 COS 的 `coscli sync`、阿里云 OSS 的 `ossutil sync`）或另一台机器（`rsync`）。

### 恢复

```bash
CONFIRM=yes infra/backup/restore.sh backups/db-20261030-033000.dump backups/uploads-20261030-033000.tar.gz
```

会先停 core 和 web，覆盖数据库和附件，再启动。不带 `CONFIRM=yes` 只打印将要做什么。

**上线前实际恢复一次**：没恢复过的备份不可信。可以先恢复到一个临时库核对条数，不影响正在用的库：

```bash
dc exec -T db sh -c 'createdb -U "$POSTGRES_USER" restore_check'
dc exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d restore_check --no-owner' < backups/db-xxx.dump
dc exec -T db sh -c 'psql -U "$POSTGRES_USER" -d restore_check -c "select count(*) from customers"'
dc exec -T db sh -c 'dropdb -U "$POSTGRES_USER" restore_check'
```

## 六、日常运维

| 事项 | 做法 |
|---|---|
| 看是否正常 | `dc ps`；`curl https://你的域名/nginx-health`；core 的 `/health` 在容器内 |
| 看日志 | `dc logs -f core`（每条请求带 X-Request-ID，可以按它把 nginx、core 的日志串起来） |
| 升级 | `git pull && dc up -d --build`；core 启动时自动执行数据库迁移。升级前先跑一次备份 |
| 外部可用性监控 | 用云监控或 UptimeRobot 之类定时访问 `/nginx-health`，挂了发告警 |
| 企业微信推送 | 浏览器测试（e2e）**只能在测试环境跑**，会真实新建报销、标赢单；测试开始前会检查推送是否开启，开着就拒绝运行 |

### 已有数据卷改数据库密码

Postgres 只在数据卷**第一次**初始化时读取 `POSTGRES_PASSWORD`。已经跑过的库改 `.env` 不会生效，要同时在库里改：

```bash
dc exec db psql -U crm -c "ALTER USER crm PASSWORD '新密码'"
# 然后改 .env 的 POSTGRES_PASSWORD，再 dc up -d core
```

### 模型接入（网页上配置）

「系统设置 → 模型接入」（只有管理员）：

- **内置厂商**：改 Key、接口地址（留空用官方地址）、协议；
- **自定义厂商**：任意 OpenAI 兼容接口或 LiteLLM 原生适配，测试连接时自动检测工具调用 / 流式 / JSON 能力和向量维度；
- **默认模型**：对话、重排的主用和备用顺序；**知识库向量模型**单独切换——后台用新模型把全部知识块重新向量化，全部成功后一次性切换，中途失败不影响现有检索（会按知识块数量调用新模型，产生费用）。

Key 放在哪里、安全到什么程度：

- 网页上填写的 Key 用 `MODEL_KEYS_SECRET` 派生的密钥加密存进数据库，只显示末 4 位；保存后由 core 推给网关立即生效。网关只放在内存里，单独重启后 core 一分钟内自动补推。
- 解密密钥在服务器 `.env` 里：它防的是**数据库备份泄露、截图、运维顺手看到**，防不住整台服务器被攻破。所以数据库备份和 `.env` 要分开存放；更有效的是在厂商后台给 Key 设消费上限或预算告警。
- 没设置 `MODEL_KEYS_SECRET` 时退回用 `JWT_SECRET` 加密；之后再设置，旧密文仍能解开，下次保存时自动换成新密钥。两个都换掉，网页上的 Key 会解不开（页面标红提示），重新填写即可。
- 网页上没填的厂商继续用 `.env`；想完全不在服务器文件里放 Key，就把 `.env` 里的 `*_API_KEY` 留空。
- 接口地址默认不能指向内网 / 本机（防止有人借服务器访问内网服务；演示模式也一样，因为演示站上任何人都能进管理员）。要接同一台机器或内网的自建模型，在 `.env` 设 `MODEL_ALLOW_PRIVATE_BASE=true`；云服务器元数据地址（169.254.169.254、100.100.100.200 等）即使打开也禁止。Ollama 跑在宿主机上时，地址写 `http://host.docker.internal:11434/v1`，Linux 上还要给 core 和 gateway 加 `extra_hosts: ["host.docker.internal:host-gateway"]`。

## 七、目前没有覆盖的

- 多台机器部署 / 高可用：现在是单机，数据库和应用在同一台；定时任务已经按「一天只跑一次」做了防重，但上传文件存在本机数据卷，多实例需要换成对象存储。
- 集中日志与报错告警（如 Sentry）：目前靠 `dc logs`。
- 后端和网关容器以 root 运行（web 容器已是非 root）；只在内网可达，风险较低，后续可以改。
