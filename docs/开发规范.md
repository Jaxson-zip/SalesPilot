## 1. 项目概述

### 1.1 一句话定位
面向 ToB 销售人员的 AI CRM：销售用自然语言完成「记跟进 → 推进商机 → 出方案报价 → 成交算提成 → 报销」，Agent 通过工具调用真实读写业务数据；行业知识以「行业包」形式可插拔。

### 1.2 范围

| 范围内（必须做） | 范围外（不做） |
|---|---|
| 4 个 CRM 模块：客户、商机、报价、合同提成与报销 | 真实的登录注册、找回密码（用假登录切换角色） |
| 三个角色：销售、销售主管（审批）、系统管理员（配置），按本人 / 本团队 / 全公司过滤数据 | 多租户、多级组织架构、可视化权限配置后台 |
| Agent：多步工具调用、毛利回退重试、写操作人工确认 | 发票 OCR、电子签章、真实支付 |
| 模型网关：注册表可接任意多家（首批混元 / DeepSeek / Qwen），兼容层抹平差异，SSE 与 tool_calls 透传 | 原生 App、小程序（Web 端做响应式，手机浏览器可用） |
| 行业包：大模型部署（完整）+ 企业办公 IT（最小版本） | 在线上传或安装行业包 |
| RAG：报销制度、部署规范、产品手册 | 通用文档问答 |
| Docker Compose 本地启动 + 云服务器部署 | K8s、CI/CD 流水线（可选加分） |

### 1.3 角色与数据权限
| 角色 | 数据范围 | 能做什么 |
|---|---|---|
| 销售 `sales` | **本人**：自己负责的客户、商机、报价、合同、报销，以及公海客户 | 记跟进、推进商机、出报价、提交报销、查看自己的提成 |
| 销售主管 `manager` | **本团队**：团队内所有成员的数据 | 拥有销售的全部权限，另外可以审批低毛利报价、超标报销和超权限折扣，查看团队看板和团队动态 |
| 系统管理员 `admin` | **全公司** | 配置行业包、产品线映射和业务规则（rules.yaml），管理用户和团队；不参与日常审批 |

**规则：**
- **数据范围由后端过滤**：每个查询都按当前用户的范围加条件（本人：`owner_id = 当前用户`；本团队：`team_id = 当前用户的团队`；全公司：不加条件）。前端只负责展示，不能靠隐藏按钮来做权限。
- **动态（Activity）可见范围跟着数据走**：一条动态挂在某个客户或商机上，谁能看到这个客户或商机，谁就能看到这条动态。所以销售在工作台看到的是「我的动态」，主管看到的是「团队动态」（可以按成员筛选），**销售之间互相看不到**。
- 客户转交、离职交接时，动态跟着客户一起转给新的负责人。
- **行业包不由销售决定**：管理员配置「产品线 → 行业包」映射；销售建商机时只选产品线，系统自动带出行业包。AI 出方案时从当前商机读取行业包，销售界面上只显示、不能改。
- 模型允许用户在 AI 输入框里切换，用来演示网关的多模型能力；可选列表来自网关 `/v1/models`，只显示支持工具调用的模型。接入哪些模型由网关的 `models.yaml` 决定。

### 3.2 服务划分与端口

```
┌──────────────────────── 浏览器 ────────────────────────┐
│  Next.js  :3000                                        │
│   ├─ CRM 页面 ──── REST (JSON) ──────┐                 │
│   └─ Agent 面板 ── SSE (/agent/chat) ─┤                 │
└──────────────────────────────────────┼─────────────────┘
                                       ▼
                    core（业务 + Agent）:8000
                    ├─ crm/     REST 增删改查 + 业务规则
                    ├─ agent/   LangGraph 状态图 + 工具
                    ├─ packs/   行业包（配置器 + 目录 + 规则 + 知识）
                    └─ rag/     入库与检索（pgvector）
                         │ OpenAI 兼容协议（含 tools、stream）
                         ▼
                    gateway（FastAPI + LiteLLM 库）:8100
                    ├─ /v1/chat/completions  /v1/embeddings  /v1/models  /health
                    ├─ models.yaml 注册表：别名 · 能力 · 分组（失败切换顺序）
                    ├─ 兼容层：请求规范化 → litellm.Router → 响应 / 流式规范化 → 错误统一
                    └─ 双链路：openai_compat（兼容接口）| native（LiteLLM 原生适配）
                         ▼
                    混元 · DeepSeek · 通义 · ……（新增模型只改 models.yaml）

                    PostgreSQL + pgvector :5432（core 独占）
```

**约束：**
- 前端**只访问 core**，不直接访问网关和数据库。
- core **只通过网关**调用大模型，代码里不出现任何厂商 SDK。
- 网关**无状态**：不连接数据库，模型配置全部在 `services/gateway/models.yaml`（进 Git），调用日志写到 stdout。
- 网关的兼容层写成**纯函数**，用各家录制的真实返回样本做单元测试。
- core 里只有 `app/llm/client.py` 能创建模型客户端，其余代码一律通过它调用。

### 3.3 一次 Agent 请求的完整链路
1. 前端 `POST /api/agent/chat`（SSE），带上 `thread_id`、`message`、`pack`、`model`。
2. core 恢复该 thread 的 LangGraph 状态（用 checkpointer 持久化到 Postgres）。
3. 进入状态图：节点调用网关，网关转发给对应模型，tool_calls 原样返回。
4. 工具执行时，core 依次推送 `tool.start` 和 `tool.end` 事件，前端更新时间线。
5. 遇到写操作工具时触发 LangGraph `interrupt`，推送 `interrupt` 事件，前端显示确认卡片。
6. 用户点击确认后，前端调用 `POST /api/agent/resume`，带上 `thread_id` 和 `decision`，图继续执行。
7. 最终回复以 `message.delta` 流式推送，结束时推送 `done`。

### 4.1 关键业务规则（写进 `rules.yaml`，代码不硬编码）
| 规则 | 默认值 |
|---|---|
| 报价毛利底线 | 25%，低于底线需主管审批 |
| 销售折扣权限 | ≤10%，超过需主管审批 |
| 提成比例 | 硬件 3%，软件与服务 8%；毛利低于 25% 的合同提成减半；按回款比例确认 |
| 客户招待标准 | ¥150/人，超标需审批 |
| Agent 毛利回退 | 最多重新配置 2 次，仍不达标就把结论交给销售决定 |

### 4.2 状态机
- **商机**：`lead` 线索 → `qualified` 需求确认 → `proposal` 方案报价 → `negotiation` 商务谈判 → `won` 赢单 / `lost` 输单
- **报价单**：`draft` → `pending_approval`（触发规则时）→ `approved` → `sent` → `accepted`（自动生成合同）/ `rejected`
- **报销单**：`draft` →（提交时校验票据和制度）未超标 `approved` / 超标 `pending_approval` → 主管 `approved` / `rejected` → `paid`

## 6. Agent 设计

### 6.1 状态图（LangGraph）

```
START → router（入口：确认过的需求卡片 / 样例图直接进出方案，其余一律进对话循环）
  └─ tool_agent ⇄ tools                               （一个模型循环处理所有对话：闲聊直接答；记跟进、查客户、改阶段、报销、算提成调工具）
       │  系统提示词每轮带上「当前这单」（阶段、下一步、最近跟进、赢单要素缺口、报价、回款，从 CRM 实时读）
       │  和「方案进行中」（上一轮追问了什么、已有需求草稿），所以「好，就这么办」「80 人」这类短句能接上
       ├─ 写工具        → confirm（interrupt）→ run_action → tool_agent
       ├─ start_solution（模型判断要出方案时调用，带上补全了指代的需求）
       │              → parse_requirement
                       → [缺信息] ask_user → END（等用户补充）
                       → configure（行业包配置器）→ price（生成 BOM 和报价）
                       → check_margin
                           ├─ 不达标且 retry < 2 → configure（带上调整提示）
                           ├─ 不达标且 retry = 2 → respond（说明原因，交给销售决定）
                           └─ 达标 → confirm（interrupt）→ save_quote → respond
       └─ 其他        → respond
```

不单独做意图分类：分类器只看当前这句话，接不上「好，按刚才说的出方案」这类上下文；
出方案作为一个交接工具交给同一个模型判断。模型不可用时按关键词规则兜底。
`evals/crm_eval.py` 用真实模型检查这个判断（转不转出方案、调哪个工具、参数对不对），提交前和基线对比。

### 6.2 工具清单

| 工具 | 读/写 | 需要确认 | 说明 |
|---|---|---|---|
| `search_customer` | 读 | 否 | 模糊匹配客户，匹配到多个时让用户选 |
| `add_followup` | 写 | **是** | 记录跟进；同一次沟通里说到的下一步（`next_step`）和阶段推进（`stage`，不含赢单 / 输单）一起填，一张确认卡、一个事务写入（`progress_service`） |
| `update_opportunity_stage` | 写 | **是** | 改商机阶段 |
| `pipeline_summary` | 读 | 否 | 漏斗统计 |
| `parse_requirement` | — | 否 | 输出结构化需求（Pydantic schema 定义在行业包里） |
| `configure_solution` | 读 | 否 | 分发给当前行业包的配置器 |
| `query_catalog` | 读 | 否 | 查询产品目录 |
| `generate_quote` | 写 | **是** | 带幂等键，重复调用返回同一张报价单 |
| `check_margin` | 读 | 否 | **规则代码计算**，不让大模型来算 |
| `calc_commission` | 读 | 否 | 按 rules.yaml 计算 |
| `search_policy` | 读 | 否 | RAG 查询，必须返回 sources |
| `submit_expense` | 写 | **是** | 提交前先做制度校验；票据未上传时只建草稿 |
| `decide_approval` | 写 | **是** | 主管审批报价 / 报销（仅 manager） |

### 6.3 Agent 行为约束（写进 system prompt）
1. **数字从工具来**：价格、显存、毛利、提成全部由工具算出，大模型只负责解释，禁止自己编数字。
2. **知识有边界**：回答制度类问题必须基于 `search_policy` 的结果并附上来源；查不到就直说「制度中未找到」。
3. **写操作要确认**：表中标「是」的工具一律走 interrupt，确认之前不写库。
4. **工具失败不瞎编**：工具报错时如实告诉用户，给出重试或人工处理的建议。
5. **最多 8 次工具调用**：超过就停下来，汇报当前进度。

## 7. 行业包规范

```
services/core/packs/<pack_id>/
├─ pack.yaml          # id、名称、描述、版本
├─ catalog.json       # 产品目录：sku、name、category、unit、cost、price、specs{}
├─ rules.yaml         # 行业专属规则（覆盖通用规则）
├─ requirement.py     # 需求 schema（Pydantic），决定 Agent 要追问哪些信息
├─ configurator.py    # 实现 Configurator 接口：需求 → 多档 BOM
├─ prompts.md         # 行业角色设定、追问话术片段
└─ knowledge/         # RAG 文档（md）
```

```python
class Configurator(Protocol):
    requirement_model: type[BaseModel]
    def configure(self, req: BaseModel, hint: str | None = None) -> list[SolutionTier]: ...
```

- 新增行业时**只能改 `packs/` 目录**，不能动 agent 和 crm 的代码。这是检验解耦是否到位的标准。
- **谁决定用哪个行业包**：管理员在「行业包配置」里启用行业包，并维护「产品线 → 行业包」映射。销售建商机时选择产品线；Agent 的 `configure_solution` 从当前商机的产品线取行业包，**不接受用户在对话里指定**。没有关联商机时，用当前用户所在团队的默认产品线。
- 大模型部署包的显存估算：`权重显存 = 参数量 × 每参数字节数`，`KV Cache = 2 × 层数 × KV 头数 × 每头维度 × 平均上下文长度 × 并发数 × 字节数`（用 KV 头数而不是隐藏维度，GQA 模型按隐藏维度算会高估约 5 倍；平均上下文默认 8192，可配置），再乘以 1.2 的余量。各模型的参数写在 `knowledge/models.json`。
- **所有价格都是模拟数据**，README 里要写明。

## 8. 接口规范

### 8.1 REST 约定
- 前缀为 `/api`，资源名用复数：`GET /api/customers`、`POST /api/quotes/{id}/submit`。
- 分页参数：`?page=1&page_size=20`。
- 认证：`Authorization: Bearer <token>`。假登录接口 `POST /api/auth/mock-login {role}` 会签发 JWT。
- 统一响应格式：

```json
{ "code": 0, "message": "ok", "data": { }, "request_id": "req_xxx" }
```

### 8.2 错误码

| code | HTTP | 含义 |
|---|---|---|
| 0 | 200 | 成功 |
| 40001 | 400 | 参数校验失败（附 `data.errors[]`） |
| 40002 | 400 | 模型能力不匹配（例如指定的模型不支持工具调用） |
| 40101 | 401 | 未登录或 token 失效 |
| 40301 | 403 | 无权限（例如销售访问审批接口） |
| 40401 | 404 | 资源不存在 |
| 40901 | 409 | 重复提交（命中幂等键） |
| 42201 | 422 | 业务规则不满足（毛利不足、超标等，附 `data.rule`） |
| 50001 | 500 | 内部错误 |
| 42901 | 429 | 模型限流（分组内所有模型都被限流） |
| 50201 | 502 | 模型网关上游错误（分组内所有模型都失败） |
| 50401 | 504 | 模型调用超时 |
| 50301 | 503 | 服务暂不可用（正式模式下无法核验账号状态等） |

### 8.3 Agent SSE 事件（`POST /api/agent/chat`）

| event | data 示例 | 前端动作 |
|---|---|---|
| `node.start` | `{"node":"check_margin"}` | 可选：显示当前步骤 |
| `tool.start` | `{"call_id":"c1","name":"query_catalog","args":{}}` | 时间线新增一行，状态为 running |
| `tool.end` | `{"call_id":"c1","summary":"筛选出 6 个配置","result":{}}` | 状态改为 done |
| `tool.error` | `{"call_id":"c1","code":50201,"message":"..."}` | 状态改为 error，显示重试按钮 |
| `node.retry` | `{"node":"configure","reason":"毛利 21.6% < 25%","attempt":2}` | 显示 retry 步骤 |
| `interrupt` | `{"action":"generate_quote","preview":{}}` | 显示 ConfirmCard |
| `artifact` | `{"type":"solution_tiers","data":[]}` | 渲染方案卡片或 BOM 表 |
| `message.delta` | `{"text":"已为…"}` | 打字机效果 |
| `done` | `{"thread_id":"t1"}` | 结束 loading |
| `error` | `{"code":50401,"message":"..."}` | 显示错误，loading 可恢复 |

### 8.4 网关接口与兼容要求（详见架构设计 §2.3）
- `POST /v1/chat/completions`：OpenAI 请求和响应格式（`tools`、`tool_choice`、`stream`）。`model` 填 `models.yaml` 里的别名（如 `deepseek-chat`）或分组名（如 `chat-agent`，按顺序失败切换）。
- `POST /v1/embeddings`（分组 `embed`）、`GET /v1/models`（别名、分组、能力表）、`GET /health`。
- **对 core 的承诺**：不管背后是哪家模型，返回都满足——
  - 工具调用一定有 `id`、`type`，`arguments` 一定是合法 JSON 字符串；
  - 流式输出严格按 OpenAI 增量格式，工具调用按 `index` 补齐，最后一片带 `finish_reason`（统一为 `stop` / `tool_calls` / `length` / `content_filter`）和 `usage`；
  - 错误一律是 OpenAI 错误结构 + 本文 §8.2 的错误码；
  - 失败切换只发生在首字节之前；流式中途断开时发送 error 事件，不静默切换。
- 新增模型：改 `models.yaml` → 跑契约测试 → 更新 `docs/模型兼容矩阵.md`，**不改代码**。

## 10. 编码规范

### 10.1 通用
- 标识符一律用英文，注释和文档可以写中文。
- 配置统一从环境变量读取，**禁止提交真实 Key**，`.env` 写进 `.gitignore`。
- 单个函数不超过 50 行，单个文件不超过 400 行，超过就拆分。

### 10.2 Python（gateway / core）
- 用 `ruff` 做格式化和 lint，所有函数都写类型注解。
- 分层：`routers` 只做参数和响应处理 → `services` 放业务逻辑 → `models` 是 ORM。业务规则只写在 services 里。
- 输入输出一律用 Pydantic schema，不在接口之间直接传 ORM 对象。
- 业务异常统一抛 `BizError(code, message)`，由全局处理器转成统一响应格式。
- Agent 工具的规范：
  - 入参用 Pydantic 校验，校验失败时返回 `{ok:false, error}` 给模型，不抛异常让图崩溃。
  - 写操作必须带 `idempotency_key`。
  - 返回值包含 `summary`（一句话，给时间线显示）和 `data`。

### 10.3 TypeScript（web）
- 开启 ESLint + Prettier，`strict: true`，禁止使用 `any`。
- 组件文件名用 PascalCase，hooks 以 `useXxx` 命名。
- 接口类型：`pnpm gen:api` 从 `docs/api/openapi.yaml` 生成 `types/generated/openapi.d.ts`；业务代码用 `types/*.ts` 的手写类型（字段注释、更窄的联合类型），`types/contract-check.ts` 在 tsc 阶段逐个断言两边一致（响应：后端 → 前端可赋值；请求：前端 → 后端可赋值）。改了后端接口的顺序：`uv run python scripts/export_openapi.py` → `pnpm gen:api` → `pnpm typecheck`，两端各有一个测试防止忘记重新生成。
- 服务端数据统一用 TanStack Query 管理，不手动维护 loading 状态。
- **样式只用 Tailwind 类名和 shadcn 组件**，颜色、间距、圆角按 §10.4 和原型执行，不随手新增颜色。

### 10.4 UI 规范（摘自原型「组件规范」页）

  - 看板：≥1024 时 5 列等分铺满；更窄时顶部是阶段切换按钮（可换行），下方只显示当前阶段的卡片。
  - 物料清单、映射表：<640 / <768 时改为逐行列表。
  - 标签页：手机上未选中的标签只显示图标，选中的显示图标加文字，保证一行放得下。
  - 唯一例外：文字过长时用省略号截断（`truncate`），鼠标悬停显示全文。

**按钮规则**
- **每个视图最多 1 个 default（黑色）主按钮**，放在标题行最右侧。次要按钮在左、主要按钮在右。
- 危险操作收进「···」菜单，用红色文字。

**AI 会话规范（DeepSeek / Ant Design X）**
- 布局：左侧会话历史 240px（按「今天 / 7 天内」分组）；中间会话区最大宽 760px 居中；输入框固定在底部，大圆角（20px）。
- 新对话显示欢迎页：标题 + 输入框 + 4 张快捷提示卡片。
- 用户消息用右侧灰色气泡；AI 回复**不用气泡**，左侧放 AI 图标，正文直接排版。
- 一条 AI 回复依次包括：`ThinkBlock`（执行过程，可折叠）→ 流式正文 → 结构化卡片（`TierCards` / `BomTable`）→ `Sources` 参考来源 → `ConfirmCard`（写操作）→ `MsgActions`（复制、重新生成、点赞、点踩）。
- 流式输出时：工具步骤逐条出现并显示转圈；正文逐字输出并带光标；发送按钮变成「停止」；结束后执行过程标题变为「已完成 N 步（用时 X 秒）」。
- `Step` 有 5 种状态：done（绿）/ running（转圈）/ retry（橙）/ wait（紫，等待确认）/ error（红）。点击步骤可展开工具的入参和出参。
- 输入框底部：行业包只读标签（锁图标，来自商机产品线）、模型选择（pill Select）、附件按钮、发送按钮；输入框下方提示「内容由 AI 生成，价格与毛利以报价引擎计算为准」。

**交互便捷性**
- 列表页顶部是 ViewBar：左边切换视图（DropdownMenu），右边是筛选 / 排序 / 选项。
- 新建和详情用右侧 Sheet，不跳转页面；记录详情页的字段点击即可原地编辑。
- `Ctrl K` 打开全局命令面板。
- 所有列表都要有空状态和骨架屏；按钮在提交期间禁用；SSE 断开后可以重试。

## 11. AI Coding 规范 ★（课程重点）

### 11.1 工具分工
| 工具 | 用途 |
|---|---|
| XBuddy（主力） | 日常编码、生成测试、代码解释、重构 |
| 其他 AI 编程工具 | 方案讨论、文档、代码审查（同样要记录） |

### 11.2 每个开发任务的标准流程
1. **写任务卡**：在 `docs/ai-log/` 新建记录，写清楚目标、涉及哪些文件、验收标准。
2. **喂上下文**：把本规范相关章节、接口契约片段、原型截图（前端任务）、相关现有代码一起贴给 AI。
3. **AI 生成**：一次只让 AI 做一个小任务，不要一句「帮我把后端写完」。
4. **人工审查**：按 §11.4 的清单逐项检查。
5. **跑测试**：没有测试的代码不能合并；测试也可以让 AI 生成，但要人工确认断言是对的。
6. **记录**：把 AI 出错和人工修正的地方写进 ai-log。这部分是评分里「对 AI 生成代码的校验与兜底」的直接证据。

### 11.4 AI 代码审查清单
- [ ] 符合目录分层，没有把业务逻辑写进 router
- [ ] 错误码、响应格式和 §8 一致
- [ ] 金额、数量这些数字是规则算的，不是大模型生成的
- [ ] 写操作有幂等或确认机制，边界值（0、负数、超大值、空字符串）都有处理
- [ ] 没有硬编码 Key、URL 或业务阈值（阈值放 rules.yaml）
- [ ] 没有凭空编造不存在的库或 API（重点查 LangGraph 的 API，版本差异很大）
- [ ] 测试能跑通，断言有意义
- [ ] 前端代码与原型一致：组件名、颜色、间距

### 11.6 Git 提交规范
- 格式：`<type>(<scope>): <描述>`，type 取 `feat` / `fix` / `docs` / `test` / `refactor` / `chore`。
- AI 生成为主的提交，在末尾加 `[AI]`；人工修正 AI 代码的提交，在末尾加 `[AI-fix]`。这样方便统计、答辩时展示。
  例如：`feat(gateway): 支持 tool_calls 流式透传 [AI]`、`fix(gateway): 修复 DeepSeek arguments 分片合并 [AI-fix]`
- 小步提交，每完成一个任务卡提交一次，**不要一次提交几千行**。
- 分支：`main` 保持可运行；功能分支命名为 `feat/<模块>`，完成后合并。一个人开发时也可以直接在 main 上小步提交。

## 12. 测试与部署

### 12.1 测试要求
| 类型 | 范围 | 最低要求 |
|---|---|---|
| 单元测试 | 行业包配置器、毛利计算、提成计算、报销校验 | 全覆盖正常、边界、异常三类情况 |
| 接口测试 | 每个 REST 接口 | 至少 1 个成功用例 + 1 个错误码用例 |
| 网关单元测试 | 兼容层纯函数：用 `tests/fixtures/` 里各家录制的返回样本，覆盖架构设计 §2.3.4 的 14 类差异 | 必须有，离线可跑 |
| 网关契约测试 | 每个模型别名跑 10 个用例：普通对话、流式对话、单工具调用、并行工具调用、流式工具调用、工具结果回传后的第二轮、JSON 输出、上下文超长报错、错误 Key 报错、分组失败切换 | 必须有（真实 Key 跑一次并录制样本，之后回放） |
| Agent 测试 | 5 条演示对话作为固定用例（用 mock 网关，结果可复现） | 必须有 |
| 前端单元测试 | Vitest：事件处理（agent-reducer）、卡片结构转换、确认卡片字段格式化、金额与时间格式化 | 必须有 |
| 端到端测试 | `tests/e2e/`：对运行中的 docker compose 环境发真实请求——健康检查、鉴权、数据权限、金额单位、出方案 → 毛利回退 → 确认 → 写入报价单、他人不能确认、请求 ID 透传到网关 | 必须有（环境没启动时自动 skip） |
