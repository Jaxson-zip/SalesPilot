# 功能模块估算参考

## 复杂度怎么判断
系统按「简单 / 中等 / 复杂」三档给每个模块估研发人天，具体人天在行业包参数的「标准模块库」里，管理员可以按自己的经验改。判断复杂度看这几点：

- 简单：单一角色、标准流程，没有外部对接，例如普通的资讯列表、个人中心。
- 中等：两三种角色或状态，有一些业务规则，例如带取消和改期的预约、带售后的订单。
- 复杂：多角色、多级审批、复杂计价规则、需要对接外部系统，或者数据量大、要求实时。

拿不准时先按中等估，并在建议和客户确认的问题里写出来，确认后再调整。

## 哪些模块通常工作量大
按默认模块库，下面这些模块的人天明显高于平均，报价时要特别和客户确认范围：

- 审批流程：审批层级、条件分支、转办和撤回都会成倍增加工作量。
- 第三方系统对接：工作量很大程度取决于对方接口文档是否齐全、有没有测试环境。
- 在线客服 / 聊天：实时消息、离线消息、图片语音，复杂度跨度很大。
- AI 能力接入、图片 / 单据识别：除了开发，还要调提示词和验证准确率，识别类建议先做样例验证。
- 数据统计报表：做成大屏、要求实时刷新时按复杂估。

## 客户没提但通常要做的
下面这些客户很少主动提，但上线一定需要，拆解需求时主动问：

- 管理后台：几乎所有面向用户的小程序 / App 都需要后台管理内容、订单和用户，报价里按「管理后台基础框架」单独计。
- 角色权限：后台不止一个人用时，需要区分管理员和操作员。
- 消息通知：预约成功、订单状态变化、审批结果提醒。
- 数据导入导出：客户有历史数据要迁移，或者要导出 Excel 对账。
- 技术架构与数据库设计：每个项目都有，系统自动计入。

## 多端和个人交付对工作量的影响
- 每多一个客户端（例如小程序 + App），模块人天按参数增加；管理后台不随客户端数量增加。
- 经济版只做第一个客户端和首期必须的模块，适合先验证业务；其余模块和客户端列为二期。
- 个人全栈交付时，所有人天按一个全栈单价计，研发人天按 AI 提效系数折算，工期按一个人算；和团队报价的区别要在方案里写清楚，让客户理解为什么工期更长。

## 估算结果怎么跟客户解释
- 先给范围再给数字：说清楚做哪些功能、几个端、包不包含 UI 和测试，再说价格。
- 用三档对比：经济版说明砍掉了什么，高配版说明多了什么保障。
- 写清楚不含的内容：服务器等第三方费用客户自付、上线后 AI 调用费另计、需求清单之外的功能按变更处理。
