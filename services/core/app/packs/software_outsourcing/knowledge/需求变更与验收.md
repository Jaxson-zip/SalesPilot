# 需求变更与验收

## 什么算需求变更
以签字确认的需求清单（或 PRD）和原型为准，下面几种都算变更：

- 新增功能模块、新增客户端（例如原来只做小程序，后来要加 App）。
- 已确认的页面、流程、字段、业务规则被改动，导致已完成的开发要返工。
- 新增第三方对接（支付渠道、ERP、短信、地图等）或对接方换了接口。
- 原来的复杂度被提高：角色变多、审批层级变多、数据量级上了一个台阶。

不算变更的：文案、颜色、图标这类小调整；开发中发现的缺陷；需求清单里写了但没写细、按常理就该有的功能（例如列表要分页）。

## 变更怎么处理和收费
1. 客户提出变更时先记下来，不当场答应「顺手改一下」。
2. 评估影响：涉及哪些模块、增加多少人天、工期顺延多少、是否影响已完成的部分。
3. 出一张变更单：变更内容、人天、费用、工期影响，客户签字（或在微信 / 邮件里书面确认）后再开发。
4. 费用按原报价同一套人天单价计算，和原报价保持一致，客户容易接受。

报价里的「需求变更与风险预留」用来消化零散的小改动；累计超过预留，或者单次变更就是一个新模块，要单独出变更单。

## 验收标准怎么写
验收标准要能逐条打勾，避免「功能完善」「体验良好」这类说不清的话：

- 功能验收：按需求清单逐个功能列验收项，每项写清楚操作步骤和预期结果。
- 兼容范围：写明支持哪些系统和浏览器（例如 iOS / 安卓近两个大版本、微信最新版、Chrome / Edge），清单之外的不在验收范围。
- 性能：只写能测的指标，例如「常用页面在 4G 网络下 3 秒内打开」「支持 N 人同时在线」，N 按客户实际规模写。
- AI / 图片识别：写「在双方确认的样例集上准确率不低于约定值」，不写「准确识别」。

## 验收流程
1. 乙方提交测试环境和验收清单，书面通知客户开始验收。
2. 客户在约定期限内（建议 5～10 个工作日）逐项验收，问题一次性列出来。
3. 乙方修复后客户复验，只复验列出的问题，不新增验收项。
4. 期限内客户既不签字也不提问题，视为验收通过；合同里要写这一条，否则尾款可能无限期拖延。
5. 验收通过后上线，开始计算维保期。

## 验收时常见的扯皮
- 客户在验收时提新需求：按变更处理，不影响本期验收通过。
- 客户找不到人验收：按书面通知的日期起算验收期限。
- 「上线后发现的问题」：区分缺陷（维保期内免费修）和新需求（另外报价）。
- 内容和数据：真实数据录入、图片素材、文案一般由客户提供，合同里写明，避免因为客户资料没到位拖住验收。
